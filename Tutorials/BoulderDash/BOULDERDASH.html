What is Boulderdash?

 

Boulderdash is an old game that consists of collecting diamonds whilst avoiding falling rocks and nasty enemies. Here is a screenshot:

 

 

It has a large number of names and variations in gameplay, such as: Skull Duggery, Rocks 'n' Diamonds, Dig Dug, Douglas Rockmore... the list goes on and on.

 

The game is played in an arena of about 30-100ish squares width and height although it varies depending on the game variation. There are several things that can exist in each level, these are:

 

The player who digs around, and is not subject to gravity.

Air, which rocks and diamonds fall through.

Earth to dig through which becomes air.

Rocks which fall through air if they are piled too high or if pushed.

Diamonds which also fall through air but can be collected if sitting still.

Metamorphosis tiles which change rocks to diamonds and vice versa.

Titanium bricks which can't be moved through or moved about.

TNT blocks which detonate when hit by a falling rock.

Fireflies who travel through tunnels hugging the right hand wall.

Amoeba who swell up filling the level and eventually collapse in a massive well of diamonds or boulders.

Rats which run around to attack the player and explode in to diamonds.

Exit blocks which open when enough diamonds have been collected.

 

Each level is played on a time limit, and a diamond target. When one of the enemies is hit by a falling rock or diamond, it detonates, destroying anything in the adjacent squares. The edge of the level is made up of either metal blocks or exit blocks. Sometimes there are not enough diamonds on the level to open the exit and more must be made by either collapsing an amoeba or pushing rocks through a metamorphosis block, or killing enough rats (which explode in to diamonds).

 

For the sake of example, let's make the play area 100 squares by 75 squares.

 

First things first

 

The first thing to do is to plan the game out. How will the object 'hierarchy' work? Well, using plain English this can be discovered.

 

“The game will be based upon the current level, which will be made up of the blocks in the level. Also in the game are the rocks and diamonds, and the time- and diamond-limit and the player and the baddies. The player will have lives left, along with the number of diamonds collected. Each of the baddies will have a current idea of what they are doing (following the walls, moving toward a specific point, expanding if it's an amoeba, etc.). The rocks and diamonds will only know whether they are falling or not.”

Main Loop

 

Now the main loop. What must the game do to run each frame? As a list:

 

• It has to move the player about.

• It has to move the baddies about according to their AI which must be updated also.

• It must make the rocks and diamonds move.

• It must update the blocks in the level if necessary.

• It must change the time and the other variables.

 

A good idea when creating a game is to order these in favor of the player. That way, when something very  close happens, like they hit the exit just as the time runs out or they just dodge out of the way of a falling rock, the game will let them do it. If it's not done like that, the game will seem unfair occasionally because the player will think that they have made it, but the order in which events occur causes them to fail. So to order them with preference to the player.

 

1. Move player and update info, so that you can get out of the way of anything falling on you.

2. Make the rocks and diamonds move incase they fall on a nearby baddie saving the player.

3. Move the baddies.

4. Update the blocks. This is after updating the baddies so that they can't follow the player on to dirt if the player digs out the way just in time.

5. Change the time so that as much as possible can occur right up until time runs out.

 

This is the basis of the main loop. If the program manages to do all these things every frame, then the game will be running and playable. The order doesn't have to be totally strict, it's a good guideline. For instance, some of those events may be handled outside of the main loop, in which case they cannot be ordered with the others.

Making some simple Level code

 

So what does the initial code for a level look like? Just a constructor like this, really:

 

Function JDLevel()

{

      This.Block[0, 0] = 0; // Initialize the block array

}

 

This is called a 'constructor' because it can 'construct' a user defined object. It is a function which is specifically designed for such a reason which is why it is called a constructor. All the variables inside it starting with 'This.' are also called 'properties'.

 

The constructor is simple enough, it just defines the first element of a two dimensional array which will represent the play area. But it obviously needs a lot more. For purposes of editing there has to be some kind of function which clears the array and initializes it. If the blocks are to be stored as numbers, then these need to be decided so that no confusion will result. A pretty logical arrangement is as follows:

 

// 0 = Air

// 1 = Earth

// 2 = Titanium

// 3 = TNT

// 4 = Metamorphosis

// 5 = Exit

 

Using these numbers as a guide we can make a function which clears the array and initializes it properly. If you want to keep it as a reminder, put the above comment in , along with the constructor for the JDLevel object. Now to write some code:

 

Function OBJ_JDLevel_MakeNew()

{

      For(x = 0; x < 100; x++)

            For(y = 0; y < 75; y++)

            {

                  If(x == 0 || x == 99 || y == 0 || y == 74) // Edge piece

                        Block[x, y] = 2; // Titanium

                  Else

                        Block[x, y] = 1; // Earth

            }

}

 

This code will clear the entire array but leave the edges as titanium. Now another function is necessary which sets a block. Blocks can be set almost anywhere, but the edge pieces must be entirely made of exit or titanium, so a function which acts as a safeguard against misplaced tiles will be useful:

 

Function OBJ_JDLevel_Set(x, y, t) // Sets a block of type t to the x and y coordinate.

{

      If(x < 0 || x > 99 || y < 0 || y > 74) // Off the edges

            Return FALSE;

      If((x == 0 || x == 99 || y == 0 || y == 74) && (t != 2 && t!= 5)) // an edge piece that isn't solid

            Return FALSE;

      Block[x, y] = t;

}

 

This function must be called to set tiles instead of setting them with the array instead. This is important, because it means that the player or anything else can never end up leaving the level if the sides are blocked. What else does the level need to do at the moment? Nothing really. So time to 'wire in' the functions that were just written. Add these two lines to the constructor:

 

      This.MakeNew = OBJ_JDLevel_MakeNew;

      This.Set = OBJ_JDLevel_Set;

 

These will make the previous function properties of the JDLevel object. That will allow those function to be accessed through the level object. Warning: In the rest of this tutorial, source code is not always given to make new functions in to properties of their objects. It's a very simple procedure and it would take up quite a lot of space to explain it each time. Whenever a new function is stated, it's up to you to make it a property of its constructor.

Function OBJ_JDLevel_DrawPos(xP, yP)

{

      gSurface.Lock();

     

      For(x = 0; x < 20; x++)

            For(y = 0; y < 15; y++)

This function takes a position on the level, and takes that to be the top left corner of the screen and draws it. It took a while but now this much has been done, it won't be too hard to continue and get a lot more done. Making the program executable in any way is always the first step. It's much harder to test the program if it can't be run to do any testing on, so generally programmers will try to keep the program executable through the whole development process. The first thing to do to test what has been done is to change this code:

 

                  Else

                        Block[x, y] = 1; // Earth

 

Changing to

 

                  Else

Then it'll fill the level with air or earth randomly so testing is much easier. After this it can be tested pretty well by substituting different values for the DrawPos function call. If you try running it when it is drawing the position (82, 0) it should crash out giving a non-initialized variable error pointing at the array. The problem lies in it trying to draw blocks which don't exist. For instance, in the DrawPos function, if x is 19 and xP is 82, the drawn block will be 19 + 82 = 101 which is off the edge of the array! The maximum position it can draw to is 80 (80 + 19 = 99, the maximum horizontal) by 60 (74 - 14 = 60 where 74 is the maximum vertical value and 14 is the lowest down block on the screen). Some error trapping code needs to be placed in the application to stop this happening. If statements could be used, but a much cleverer approach would be to use the Max and Min functions. The xP variable must be a maximum of 80 but can be smaller, and a minimum of 0 but can be larger. The code using Max and Min looks like this and goes at the start of OBJ_JDLevel_DrawPos:

 

      xP = Min(Max(xP, 0), 80);

      yP = Min(Max(yP, 0), 60);

 

This means it will pick the greater value of 0 and xP, so if xP is less than 0 it will select 0 instead, then it will select the minimum value of 80 or the previous result, so if xP is bigger than 80 it will pick 80 instead. This code is almost illogical, so if you want a simpler version, it would look like this:

 

      If (xP < 0)

            xP = 0;

      If (xP > 80)

            xP = 80;

      If (yP < 0)

            yP = 0;

      If (yP > 60)

            yP = 60;

 

It is much more obvious what it does this way, but it will be a bit slower (not that either way will be slow at all) and the previous way is more compact. Use whichever method you prefer, but later on the Min/Max version shall be used for other similar problems.

 

Some code towards making an editor

 

An editor is no use if you can't scroll around and take a look at the level. Let's put some code in the level object which allows it to be scrolled around. First of all, the level object really needs some variables to record where the screen is on the level, so put some new variables in the constructor like such:

 

      This.xPos = 0;

      This.yPos = 0;

 

This will set what part of the level is currently being drawn. Another function would be useful which just draws the current position:

 

Function OBJ_JDLevel_Draw()

{

      DrawPos(xPos, yPos);

}

 

Very simple, now add it as a property of the level object like before. A scroll function is easy enough, it will take two inputs, the amounts to add on to the x and y values. In mathematical notation, these are usually called 'delta x' and 'delta y', where delta means 'change of'. So the abbreviations dX and dY are used here. The code is:

 

Function OBJ_JDLevel_DoScroll(dX, dY)

{

      xPos += dX;

      yPos += dY;

     

      xPos = Min(Max(xPos, 0), 80);

      yPos = Min(Max(yPos, 0), 60);

 

      Draw();

}

 

The top code adds on the delta values, then there is the familiar limiting code, and then a call to the draw function to draw the screen (this may seem like there's a lot of unnecessary functions but later on it will become clear why it is like this). The name is DoScroll to avoid the case correction of the name Scroll, just another one of those personal preference things.

 

Adding this code as a property of the JDLevel object lets the user scroll around. All that is needed now is some code in the main loop to actually let the user scroll. Something like this for a supplement to :

 

Level.Draw();

 

While(TRUE)

{

      yScr = 0;

      If(IsKeyDown(Keyboard.LEFT))

            xScr--;

      If(IsKeyDown(Keyboard.RIGHT))

            xScr++;

      If(IsKeyDown(Keyboard.UP))

            yScr--;

      If(IsKeyDown(Keyboard.DOWN))

      If(xScr || yScr)

}

 

Run the program and if everything is in order, it should be scrollable with the arrow keys! As you can see, it may be taking a while but it's getting there.

Saving and loading

 

Saving a level to disk is simply a matter of finding and recording all the vital information in a specific order, and loading it is just the same function back to front so it reloads all the vital information, and sets it up again. You will probably want to get familiar with the binary object if you're not already, it features heavily in saving and loading.

 

Almost all the vital information is held in the array Level.Block[]. Each number in the array is a value between 0 and 21 inclusive, so a byte is enough for each. If you don't know, a byte has 256 different values so a byte is more than enough. If you were being very efficient, you could use only 5 bits per block but that's beyond the scope of this example.

 

The only other vital information is the diamond limit and the time limit. A reasonable maximum diamond limit is 1000. As already seen, the time limit is between 150 and 3000. Neither of these values will fit in to a byte, but they will fit in to two bytes which is called a Word. A Word has 65536 different values.

 

Now the size of the save file needs to be calculated. As you probably know by now, there are 7500 squares, at a byte each, that totals 7500 bytes. Then there are two variables which take up 2 bytes each, which is another 4 bytes. Therefore the total is 7504 bytes. Fortunately all the levels will be this size, as there is no capacity for it changing.

 

The function is starting to take form:

 

Function OBJ_JDLevel_Save(fName)

{

      bOut = New Binary();

      bOut.AllocateData(7504);

 

Then there must be a couple of for loops to go over every position in the block array and save it in to the binary object. Another variable to record the writing position is also necessary, let's call it wPos:

 

      wPos = 0;

      For(x = 0; x < 100; x++)

            For(y = 0; y < 75; y++)

                  bOut.SetByte((wPos++), Block[x, y]);

 

Then save the other variables at the end, and save it to disk:

 

      bOut.SetWord(7500, DiamondLimit);

      bOut.SetWord(7502, TimeLimit);

 

      bOut.SaveData(fName, TRUE, 0, 0, 7504);

 

Remember to delete the binary object (it won't affect the file on the disk) and it's finished:

 

      Delete bOut;

}

 

Now if you can separate out the code from there, you should make it a new function of the level object. Once that is done, make it part of the program by entering this code in to the main loop:

 

      If(IsKeyDown(GetAscii("S")))

      {

            fSelect = New Selector();

            success = fSelect.SaveFileDialog(gWindow, "Select save file...", "JamaDash Level|*.JDL||", 0, "Level.JDL", GetApplicationDirectory(), ".JDL");

Function PointContent(x, y)

      If(Level.Block[x, y] > 0) // Not air so can't be anything else

Improving the scrolling

 

After so much hard work, I'm not going to let you off that easily! Now it's time for a fairly hard section...

 

The scrolling may seem perfect but in if you think about it, it wasn't written to run very fast. Whenever the screen moves, it redraws everything in it. If you've got everything so far to work, then you will have been able to drive the little player graphic around the level, and will see that practically all the time the level doesn't need to be redrawn, only a very slim set of tiles need to be redrawn.

 

This section isn't for speed reasons. On my computer (850 MHz Duron w/ ATI Radeon) the screen scrolls easily fast enough. Rather, you should realize in this section that the simplest algorithm is rarely the best one. Just because an algorithm has more source code doesn't mean it's necessarily slower. Sometimes you have to write a lot extra to make it run faster.

 

Let's take a look at the function for scrolling inside :

 

Function OBJ_JDLevel_DoScroll(dX, dY)

{

      xPos += dX;

      yPos += dY;

     

      xPos = Min(Max(xPos, 0), 80);

      yPos = Min(Max(yPos, 0), 60);

 

      Draw();

}

 

Thankfully there isn't anything complex left in from earlier. The only line that needs changed is the Draw(); line at the end. Add a new function to the JDLevel object called DrawPart with this code:

 

Function OBJ_JDLevel_DrawPart(xa, xb, ya, yb)

{

      gSurface.Lock();

     

      For(x = xa; x < xb; x++)

            For(y = ya; y < yb; y++)

                  gSurface.Copy(BlockImg, x*32, y*32, 32*Block[xPos +  x, yPos + y], 0, 32, 32);

     

      gSurface.Unlock();

}

 

Similar to DrawPos, but will now only draw between xa and xb, from ya to yb using the Level object's scroll position variables. We can use this to fill in only the blocks that need to be drawn. To scroll the actual screen there is a built in function. Look in the help file under Object Reference, Windows and Graphics, Surface, Scroll. Take a look if you're not familiar with it.

 

The surface needs to be scrolled corresponding to the values of dX and dY. But if you remember the function, xPos and yPos are capped at 0 and 80 or 60. So although dX and dY are always passed to the function they are not always applied. For instance, if the player is pushing against the left hand edge, the screen would be trying to scroll with dX = -1 (left). But the screen won't scroll because it can't display past the left edge, which is why xPos is capped at 0. If scrolling the surface was introduced, it would need to know whether or not dX was really applied or whether the xPos was capped. Using some hard algorithm crunching, the solution can be found. It looks like this:

 

Function OBJ_JDLevel_DoScroll(dX, dY)

{

      dX += xPos;

      dY += yPos;

     

      dX = Min(Max(dX, 0), 80);

      dY = Min(Max(dY, 0), 60);

 

      // Now (dX - xPos) is the applied scroll value, similarly (dY - yPos)

     

      xPos = dX;

      yPos = dY;

}

 

You are might be wondering how this works unless you're fairly mathematical. Let's take a look at what the final result in the comment really means:

 

(dX - xPos)

 

What has happened is that dX has been reassigned the value of xPos after it has been scrolled. Taking away the original will result in the amount of scrolling done.

 

For example, let's assume that dX was not capped, so that it was added to xPos. In that case, dX is equal to xPos + the original dX passed to the function. So the formula expands to:

 

((xPos + dX) - xPos) which simplifies to dX

 

And if it was capped, then dX would just be xPos because no scrolling took place, in which case:

 

((xPos) - xPos) which is equal to 0, confirming that no scrolling has been done!

 

Hopefully that's cleared up any confusion. If it hasn't try running a few test calculations on paper to work out what is happening. Well, even if you don't understand, you should see that the important values that were required have been found. Now to scroll the screen with them using the scroll function. Put this line after the comment:

 

      gSurface.SCROLL(-32*(dX - xPos), -32*(dY - yPos));

 

Auto-caps messes up this function name but never mind. Now only one thing is left. Using DrawPart to fill in the remaining squares.

 

This is actually fairly simple. Just using If statements it can be deduced what scrolling has happened. xPos and yPos need to be set before calling DrawPart so careful attention is needed there. Thankfully, only left-right scrolling or up-down scrolling can occur at once which saves a lot of work sorting this out. Here's the code anyway, the end of the DoScroll function should look like this:

 

      // Now (dX - xPos) is the applied scroll value, similarly (dY - yPos)

      gSurface.SCROLL(-32*(dX - xPos), -32*(dY - yPos));

     

      If ((dX - xPos) > 0)

      {

            xPos = dX;

            yPos = dY;

           

            DrawPart(19 - (dX - xPos), 20, 0, 15);

      }

      Else If ((dX - xPos) < 0)

      {

            xPos = dX;

            yPos = dY;

           

            DrawPart(0, 1 - (dX - xPos), 0, 15);

      }

      Else If ((dY - yPos) > 0)

      {

            xPos = dX;

            yPos = dY;

           

            DrawPart(0, 20, 14 - (dY - yPos), 15);

      }

      Else If ((dY - yPos) < 0)

      {

            xPos = dX;

            yPos = dY;

           

            DrawPart(0, 20, 0, 1 - (dY - yPos));

      }

      Else

      {

            xPos = dX;

            yPos = dY;

      }

}

 

A sizeable chunk of code! It is really just going through the possibilities though. Running the game should, maybe, make things work. And what's the result? Oh great, nothing has changed.

 

Now ask yourself, did you think it was worth it? You may well say a big 'No' to that. It seems like a lot of pointless roundabout coding to achieve what's already been done. Take a little think though. Before it was drawing the full 20 * 15 = 300 tiles every time it scrolled. Now it's either drawing 15 or 20, and on average that's 17.5 tiles drawn per scroll. It may seem complicated but it isn't too complex. The loop goes through the numbers 5, 4, 3, 2. The turning is based on modular four arithmetic. This means that:

 

5 = 1 (%4)

4 = 0 (%4)

3 = -1 (%4)

2 = 2 or -2 (%4)

 

Now that means first it will try the direction plus one (a turn right), then just the normal direction (straight forward), then the direction minus one (turning left) and lastly the direction plus two (turned around). Think of a clock which starts at 3pm (as in right), then winds backwards to 6 hours. The hand will be in the same position as if it wound forward six hours. If it can't expand further and it's under 12 squares, it dies and turns in to boulders. If it gets too big, for instance over 100 squares then it will also die in to boulders straight away to add another gameplay aspect, and also to stop it getting too complex. The amoebae must be confined by some obstacles to be useful to the player. Also like classic Boulderdash, the amoeba will cause the baddies to spontaneously combust if it grows on top of them, but will strictly leave the player alone.

 

The easiest way of keeping account of its mass is to use two variables, Mass and idleMass. The Mass variable increases as the amoeba does. The idleMass variable is the amount of squares of it which cannot expand further. Clearly if these are kept track of properly, then when they are both equal the amoeba cannot expand any further. Also, the Mass variable can be used to check if it's getting too big, or if it's too small to collapse.

 

The problem with the amoeba is that it takes multiple squares, so it might as well be many different amoeba. This is, as you may know, the solution as to how it could work. If there were a new baddie type, called a AmoebaChild which for all intents and purposes looks, acts and seems like an amoeba in the game, the problem becomes easy. The key thing is that the AmoebaChild won't think like the amoeba. The AmoebaChild could report back to its parent so the original amoeba square is like a 'control center' that grows drones out. Of course, the people playing the game won't be able to tell the difference because they'll appear the same and all act as one unit. The drone AmoebaChilds must know who their parent is as well, so that has to be recorded when they are 'born'.

 

This is all fully possible, but the AI listing is quite long.

Rat AI

 

The rat works differently from the firefly and the amoeba. It is more like the firefly, however it bases whether it turns a corner on logical decision making. To get a clear image in my mind of how algorithms work, the best thing I can do is leave the computer and get a pen and some paper, and sketch it out until it's figured out. For instance:

 

 

Well it might make me look insane but it did help me think about it. If you can't read my handwriting then here's what the rat should do:

 

1. Find out all the possible directions it can go.

2. All the directions which are blocked are impossible, of course.

3. Figure out how useful it will be to travel in each direction, with regards to getting to the player.

4. Turning around is a bad direction to travel, even if it is the way to the player. (This discourages the rat from repeating the same mistake over and over).

5. Travel in the direction which is the best.

 

In essence, this is just a simple way of guessing the probability of finding the player in any of the directions that can be travelled. This is called using 'thresholds'. Here is the code:

 

Function OBJ_JDBaddie_RatThink()

{

      bestThreshold = -1; // All negative thresholds are really bad, so lets set the minimum to -1.

      bestDir = -1; // -1 is a dummy value representing 'no square' at the moment.

      For (n = 0; n < 4; n++)

      {

            dThreshold = 10; // Start off with ten points for this direction

            space = PointContent(xPos + DirToDx(n), yPos + DirToDy(n));

            If (space == 8)

            {

                  // Kill player

            }

           

            If (space != 0) // Not air

                  dThreshold = -100; // So give it a really bad score!

           

            If (n % 2 == 0) // Vertical

                  If (Sign(Player.yPos - yPos) == Sign(DirToDy(n)))

                        dThreshold += Min(Abs(Player.yPos - yPos), 10); // Bonus for going towards player

            If (n % 2 == 1) // Horizontal

                  If (Sign(Player.xPos - xPos) == Sign(DirToDx(n)))

                        dThreshold += Min(Abs(Player.xPos - xPos), 10);

           

            If (n == dir)

                  dThreshold += 1; // Add a bonus if you're continuing in the same path

           

            If (n == (dir + 2) % 4) // If it's turning around

                  dThreshold /= 2; // Get 50% knocked off

           

            If (dThreshold > bestThreshold) // Was it the best result so far?

            {

                  bestDir = n;

                  bestThreshold = dThreshold;

            }

      }

     

      If (bestDir != -1) // If there's a decent square to move in to

      {

            dir = bestDir;

            MoveToSquare(xPos + DirToDx(dir), yPos + DirToDy(dir));

      }

     

      thinkTime = System.GetElapsedTime() + 75 + Random(75); // Think again.

}

However this is just an enemy in a simple 2d game so the previous function is good enough. The problem is if it's only returning one file, it won't use an array, but the main loop always loads the level through an array. A function which uses the selector and then finds an array from it looks like this:

 

Function GetLevelData()

{

      dSelector = New Selector();

     

      done = dSelector.OpenFileDialog(gWindow, "Select mission(s)...", "JamaDASH Levels|*.JDL||", 0, "", GetApplicationDirectory(), "JDL", Selector.FILEMUSTEXIST, Selector.ALLOWMULTISELECT);

     

      If (done) // Files were selected

      {

            If (dSelector.HasManyFiles()) // It's an array (easy)

                  This.LevelName = dSelector.GetFiles();

            Else // Just a single level that needs to be put in an array

            {

                  This.LevelName[0] = dSelector.GetOneFile();

                  This.LevelName[1] = ""; // No other levels

            }    

      }

      Else // Didn't select any levels, so just use the built in ones

      {

            This.LevelName[8] = "";

            For(lev = 0; lev < 8; lev++)

                  LevelName[lev] = "Mission" + (lev + 1);

      }

     

      Delete dSelector;

}

 

A call to this function can replace the code that decides the level names at startup. This will allow users to select their own mission set.

A retrospective view

 

After all that work, what is the quality of the result?

 

Well, the game can suffer slightly from slowdown when there's a lot of minerals flying around. As always it depends on what computer is being run on. It isn't really an issue, because the way it was designed was supposed to be relatively simple to understand. The minerals could have been optimized for speed which would have prevented the slowdown but been difficult to understand.

 

There are a few bugs in the code. You can walk directly in to the path of a flow of falling boulders. This isn't too hard to fix, and you can if you want. I prefer to take the lazy route and call it a 'feature' of the game.

 

The original plan for the main loop looked like this:

 

1. Move player and update info, so that you can get out of the way of anything falling on you.

2. Make the rocks and diamonds move incase they fall on a nearby baddie saving the player.

3. Move the baddies.

4. Update the blocks. This is after updating the baddies so that they can't follow the player on to dirt if the player digs out the way just in time.

5. Change the time so that as much as possible can occur right up until time runs out.

 

This wasn't followed precisely. The baddies where on a separate time control from the players (I wanted to demonstrate both ways of controlling groups of objects, I prefer the way the Baddies where timed with thinkTime). The blocks in the level never really needed updating in the main loop so that was missed out. Other than that, it was pretty much the same order.

 

Any program can be improved. In what way way this program lacking?

 

Well, first of all the bugs could always be fixed.

 

The Rat AI could be improved. Perhaps some code could be put in to ambush the player, where if the rat is sufficiently far away, and it finds a dead end tunnel, it will sit and wait there for the player to near, and then run at them when they get near. There isn't anything wrong with the Rat's AI as it is, but AI is never perfect and always has stupid shortcomings that people just have to figure out.

 

The scrolling could be made so it didn't snap to a 32 spaced grid. This would require all the level drawing commands to be changed to accept screen coordinates instead of level coordinates and then translating back. The mod % operator would be needed quite a lot, and generally it's a lot trickier. It is possible though, and will improve the visual quality of the game quite a lot.

 

The boulders could fall smoothly instead of jumping down squares. The baddies could move smoothly instead of jumping around squares. The player could also move smoothly, instead of jumping around squares. This sort of thing is harder to implement, it requires precise timing on the part of the programmer. It would have to be calculated with percentages, and would probably be easiest to implement with the baddies, if you really want the challenge.

 

The level editor could be integrated and improved a great deal. This would allow people to make their own levels with ease. And it could be integrated with the actual game, but that's all a bit over the top because there wasn't even a main menu to this game.

 

And of course, there's the things which can be added for fun. This section is basically for the enthusiastic reader who wants a challenge.

 

New square type: Teleportation squares. These would scan through the level from left to right, top to bottom and find the next teleportation square then send whatever hits them there.

 

New mineral type: Cocoon. It falls down and when it hits the ground, it explodes in to fireflies. Most of the code for this is already implemented, so to make it more challenging, they could be pushed around and only break when they fell over five squares.

 

New baddie type: The butterfly. It follows the left hand wall, explodes in to diamonds and is very fast.

 

New gameplay element: Oxygen supply. Taking an idea from Manic Miner on the ZX Spectrum, why not make the player subject to the detriment of having to breathe oxygen. It could be recharged at oxygen points so the player can't wander around too long without pegging it. This would make the game 4.7 times more difficult.
